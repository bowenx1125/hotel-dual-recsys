# FYP1 目录导览与人工推进指南

读者：项目负责人。进展数字统一看 [项目报告](../PROJECT_STATUS.md)，本指南讲文件用途和操作方法。

## 1. 先理解系统在做什么

路线是：住客评论 → 按清洁/早餐等方面整理 → 与附近酒店比较 → 区分可改变与难改变的问题 → 输出经理建议及证据。你负责定义“什么建议有用”和“什么结论可靠”，agent 帮你实现与检查。

目前：经理端可演示，研究已覆盖 515,738 条评论 / 6 城市 / 1,493 家酒店；Manager 界面只展示原 24 家样例中的 22 家。游客选酒店的推荐端尚未完成。研究原型能运行，不表示已经证明能提高评分、预订量或利润。

## 3. 你现在可以做什么

### 第一步：自己看一遍 Demo（30 分钟）

在终端运行：

```bash
cd /Users/xubosmell/Desktop/FYP1
.venv-demo/bin/python -m streamlit run demo/app.py --server.headless true --server.port 8501
```

打开 http://localhost:8501 。选 3 家样例酒店，分别记录：系统发现了什么、建议改什么、依据够不够、文字是否看得懂。把观察交给协调者，明确区分“我的观察”和“我猜测的商业效果”。结束时在启动终端按 Ctrl+C。

### 第二步：查看自动标注报告，无需自己填 label

用户已选择 Grok 初标、Claude 独立盲审、Codex 分层抽查。当前协议见 [模型标注协议](MODEL_ANNOTATION_PROTOCOL.md)，整体实验顺序见 [科研方案](RESEARCH_PLAN.md)。旧 126 项人工表保留为历史试用材料；没有 label 是因为以前的导出器故意生成空白填写表，不是数据库丢失标签。

新流程从完整源数据抽取覆盖 6 城市、7 方面的诊断集，最终标签和审计记录在本机 `outputs/autonomous/private/model_annotation_rounds/`；无评论原文的统计报告在 `outputs/autonomous/model_annotation/`。你不必逐条核验，也无需找第二个人。两模型有分歧或不确定时由 Codex 最终裁决，原文含糊仍保留 unresolved；不能把一致答案直接叫作真实准确率。

### 第三步：和导师确认一期目标

建议先把一期目标限定为“酒店经理的可靠诊断和可操作建议”。请确认：经理应该使用它做什么决定、什么样的建议不该给、怎样评价建议是否有用。游客端与收益因果验证各需额外数据与评测，宜单独安排，避免所有方向都只做到一半。

## 4. 接下来由谁做、交付什么、为什么

| 顺序 | 你负责 | Cursor 负责实现 | 协调者负责审计 | 交付物与理由 |
|---|---|---|---|---|
| P0 自动标注 | 无需逐条填写 | Grok 标注、Claude 盲审、断点与一致性统计 | 来源、盲化、全部分歧及分层一致项抽查 | 产生有不确定性记录的模型参考标签 |
| P1 规则对齐 | 确认哪些建议可执行，证据不足怎么办 | 统一 Demo 和离线策略的门槛与拒绝建议 | 覆盖不足、位置不可操作、所有策略输出一致 | 先保证“建议不乱说” |
| P2 全量界面对接 | 验收 3–5 家酒店完整流程 | 将 515K 研究结果接入 Manager 页，显示来源/覆盖/限制 | 不混淆历史快照与全量结果，不捏造指标 | 得到完整可展示的项目 |
| P3 公平实验 | 理解比较标准与结论范围 | 基线/消融、时间切分、模型独立评价 | 泄漏、循环评价、覆盖率、区间与负结果 | 回答“哪些设计有用”，业务有效性另外验证 |
| P4 论文 | 定义贡献、核对文献、解释局限 | 根据已审计结果生成表格和辅助文本 | 结论与证据一致，未做工作不写已做 | 从原型走向可评审论文 |

每一行再拆成小任务写入 AGENT_TASKS.md，完成一项审计一项，不把整张表一次交给多个 agent 自动改同一套文件。P1 的纯规则测试可以与自动标注并行，涉及已标注结果的实验必须等数据就绪。

## 5. 创新点应该怎样讲

当前贡献方向是：**把附近酒店比较、建议可操作性、评论测量可靠性结合起来，必要时不给建议。** 举例（仅说明逻辑）：位置差是诊断，清洁流程才可能是可执行的改进；只有两条相关评论时，应降低信心或暂不给结论。

这不是已经证明的新算法。需要通过“去掉可操作限制会怎样”“去掉可靠性/拒绝机制会怎样”“相比只修最差方面是否更合理”等对比，证明每部分的价值，再核对原始文献确认新颖性。贝叶斯收缩、地理近邻、交叉拟合各自是已有方法，不能把使用它们直接说成首创。

原先关于竞争者同时改进导致收益下降的命题目前证据不足；现有预测提升很小且置信区间跨零。论文应保留这个负结果，聚焦当前能够支持的经理决策问题。

## 6. 如何使用 Cursor 与协调者

Cursor CLI 已安装并用用户账户登录；用下面命令可检查状态或启动（换机器需重新设置）：

```bash
~/.local/bin/agent status
cd /Users/xubosmell/Desktop/FYP1
~/.local/bin/agent
```

可以给协调者这样的任务：

> 按 AGENTS.md 推进 P1：先列出要统一的建议规则和验收条件，再派 Cursor 实现。不要改实验门槛或既有结果；完成后你独立审计，并按已有授权同步 main。

标准协作顺序：你确定目标和判断标准 → 协调者分解、分配文件 → Cursor 写代码和测试 → 协调者独立检查 → GitHub 同步与 CI → 你验收产品行为。不要把“Cursor 写完”当成“已经验收”。

现有订阅优先用于这些必要的实现与修复；无法从当前 CLI 状态准确判断剩余额度，不承诺或制造无意义的“耗尽”。遇到额度不足先记录，不擅自启用额外付费。

Cursor CLI 会读取根目录 AGENTS.md 与 CLAUDE.md，见 [官方使用说明](https://cursor.com/docs/cli/using)；非交互模式和权限见 [Headless](https://cursor.com/docs/cli/headless) 与 [Permissions](https://cursor.com/docs/cli/reference/permissions)。具体调用以本机 `agent --help` 为准。
