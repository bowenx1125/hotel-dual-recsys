## 二、核心结论（先说结论）

> **用现有数据无法"证明"酒店收益增加。**

理由：数据集是 Booking.com 欧洲 51.5 万条评论，字段只有评论文本、日期、评分、坐标、评论量。**没有房价（ADR）、没有间夜/入住率、没有订单、没有成本**。收益 = 价格 × 销量，两项都缺。项目自身也已记录这一点：`FACTS.json` 的 Wave 6 明确写着 `no_ips_snips: true`、`no_roi: true`、`no_demand_lift: true`;声明台账 CLAIMS_LEDGER 把因果措辞标为 `FORBIDDEN`。

**能做到的是把"收益证明"拆成三段，逐一补上，并诚实标注每段的可信等级：**

```
① 建议 → 方面分改善   （准实验估计，可用现有数据做）
② 方面分改善 → 评分/订单量提升  （准实验估计，可用现有数据做）
③ 评分 → 收益         （必须接外部弹性系数，是"推算"不是"实测"）
```

第 ③ 段无论做得多细都只是**带引用的推算**，要变成"证明"必须有真实 A/B（酒店伙伴或 OTA 合作）。这一点应写进论文局限与声明台账，不能靠话术绕过 —— AGENTS.md 第 6.5 条已明令"启发式权重、场景滑块与合成测试不能充当真实收益证据"。

## 四、关键技术发现（决定了怎么做）

体检面板（`data/processed/hotel_aspect_quarter_v2.parquet`）后确认：

1. **下游结果变量已经存在**：面板里每个酒店-季度都有 `mean_reviewer_score`（季度均分，均值 8.45）和 `total_reviews`（季度评论量，均值 40.5）。不需要重新跑原始 CSV 就能搭收益链路。完整季度酒店-季度共 9,960 格，1,493 家酒店。
2. **现有 Wave 5 的因变量是自指的**：它用 `smoothed_net` 当 y，而"处理"本身就是方面情感改善 —— 相当于用尺子量自己。必须换成 `mean_reviewer_score` / `total_reviews`。
3. **离散事件功效不足**：456 个严格事件只分布在 2016Q2–Q4 三个季度（122 / 168 / 166），且季度评分变化标准差达 **0.66**。以 456 个样本做匹配 DiD，可检出效应量约 ±0.08 分，非常勉强。
4. **建议改用「连续处理 + 交叉折」设计**（关键）：把处理定义为一侧折（fold A）的 `Δsmoothed_net`，结果用另一侧折（fold B）的评分变化来测。项目已有 A/B 交叉折基础设施（`smoothed_net_A` / `smoothed_net_B`、crossfit 配置），这样能**切断"同一批评论既产生方面提及又产生评分"的机械耦合**，样本量也从 456 提到数万级别。这是本项目现有资产里最有价值、但还没被用起来的识别杠杆。
5. **Location 是不可变负对照**（配置里已声明 `immutable_negative_control_aspect`），可直接用来做安慰剂检验。

## 五、分阶段路线

### P1 · 基线冻结（0.5 天）
目标：在与同事一致的基线上开新分支，保证结果可比。
- 新建分支 `codex/revenue-impact`，不改动 main。
- 记录环境、依赖、输入哈希到新的运行目录，不覆盖 `outputs/autonomous`。
- 验收：`unittest` 236/238（两项环境失败登记为已知）、`--small-fixture --verify-only` Wave 0–10 通过。

### P2 · 效应估计：方面改善 → 下游结果（2–3 天）★核心
目标：得到 β̂_a = "方面 a 的净情感每改善 1 单位，后续季度酒店评分/评论量变化多少"，带置信区间。
- 构建酒店-季度结果表（`mean_reviewer_score`、`log(total_reviews)`）。
- 连续处理：Δ`smoothed_net_A`（折 A 检测），结果：折 B 的 Δ 评分 / Δ log 评论量。
- 双向固定效应（酒店 FE + 城市×季度 FE），酒店层聚类稳健标准误；城市层用 wild bootstrap（城市只有 6 个）。
- 三项必做核验：① 前置趋势/先导检验（用 t 期改善预测 t−1→t 变化，应≈0）；② Location 安慰剂（应≈0）；③ 逐城市留一法稳定性。
- 产出：新 Wave 11 目录、`effects.json`、事件研究图数据、负结果原样保留。
- 验收：效应符号稳定、CI 报告完整、安慰剂通过或如实记录失败。**若为负结果，保留并写入论文**（AGENTS.md 第 6.1 条要求保留负结果）。

### P3 · 算法优化：从启发式权重到期望收益排序（1–2 天）
目标：`scoring.py` 里那句 `weights_are_design_choices: True` 变成 `False`。
- 新策略 `expected_gain`：`score(a) = β̂_a × 可达改善量 Δ_a × 可靠性_a × 可操作性_a ÷ 成本代理_a`，其中 Δ_a 取该方面历史改善分布的分位数（如 P75），而不是拍脑袋。
- **保留**现有证据闸门（≥5 次提及、可靠性≥0.3、≥2 家参照、Location 永不作为行动、证据不足即弃权）—— 这是本项目已成立的贡献，不能为了优化而拆掉。
- 训练/评估严格按时间切分：β̂ 用 2016Q4 及之前拟合，2017Q1–Q2 留出评估。
- 产出：`src/recommendation/scoring.py` 新增策略 + 配置 + 单测。

### P4 · 离线策略评估：新策略真的更好吗（1–2 天）
目标：把 `no_ips_snips: true` 翻掉。
- 定义奖励 R = 后续季度评分变化（折 B）。定义日志策略 π₀ = 历史上"实际改善了哪个方面"的经验分布。
- 用 IPS / 双重稳健（DR）估计新策略与旧启发式的期望奖励差，酒店聚类 bootstrap 出 CI。
- 报告覆盖度、弃权率、位置违规率、以及**自然依从子集的实测提升**（标注为非因果佐证）。
- 明确写入局限：方面改善不是随机分配的，OPE 是观察性的，不等于因果。
- 产出：`outputs/runs/<run>/ope.json` + 新 Wave 12。

### P5 · 收益折算与不确定性（1 天）
目标：把评分变化翻译成钱，且把不确定性摆在台面上。
- 建一条可审计的换算链：`Δ收益 = Δ评分 × 弹性 × ADR × 房量 × 365`。
- **弹性和 ADR 必须来自外部文献/公开行业数据，逐一核对原始出处后再写入**（AGENTS.md 第 6.6 条：未核验的主张要标明待核验）。在未核对前不填任何具体数字。
- 做敏感度网格 + 盈亏平衡分析（改善成本低于多少才划算）。
- 结论一律标注 **"模型推算（projection），非实测收益"**。

### P6 · 论文与 Demo 同步（1 天）
- 更新 `FACTS.json` / `CLAIMS_LEDGER.md`（新增声明条目：算法更优 = 待定；收益 = 推算，非实测）。
- 论文方法/结果章替换占位数字；局限章写明"需真实 A/B 才能称为收益证明"。
- Demo 若要加收益面板，必须显著标注"推算值，含外部假设"。
